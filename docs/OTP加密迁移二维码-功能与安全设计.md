# OTP 加密迁移二维码｜功能、安全与实现说明

**版本：** 1.2（单条与全量 OTP 迁移已实现）  
**日期：** 2026-08-25  
**目标：** 让用户在两台设备之间，离线迁移单条或全部 OTP 验证码。导出内容在本地加密；用户可使用访问密码、有效期，或同时使用两者。

## 一、产品边界

迁移二维码用于用户主动、近距离地迁移 OTP，不上传 OTP 密钥、访问密码、二维码内容或导入记录。它不取代微信加密 `.bak` 文件：二维码适合面对面换机或临时迁移，文件适合长期留存、微信转发和完整数据备份。

| 场景 | 推荐入口 | 传输范围 | 接收方式 |
|---|---|---|---|
| 迁移一条验证码 | OTP 条目长按 → **生成迁移二维码** | 单条 OTP | 首页“扫码添加”扫描后导入。 |
| 迁移全部 OTP | 首页 OTP 导出菜单，或数据管理 → 微信导入导出 → **导出全部 OTP 为二维码** | 所有 OTP 条目；不含密码账本、设置、回收站或二维码历史 | 接收方连续扫描同一组二维码，收齐后一次性导入。 |
| 完整备份或长期保存 | 数据管理 → 导出至微信 | 加密 `.bak` 快照 | 从微信文件中选择 `.bak` 并恢复。 |

> **二维码迁移至少要启用一种保护：访问密码或有效期。** 访问密码为可选的 **6 位及以上**文本；有效期可选 5 分钟、15 分钟、1 小时、24 小时或不设有效期。两者都不设置时无法生成二维码。

当用户只设置有效期而不设置密码时，二维码在有效期内可被任何拿到二维码的人导入。因此页面会明确提示其只在可信环境出示。有效期仅由导入设备的本地时间检查，不能提供远程撤销、全局一次性使用或防止修改系统时间的保证。

## 二、与现有模块的协同

功能不增加主导航工具页，而是进入用户已经理解的验证码、导出和扫码路径。

| 现有模块 | 已接入的迁移能力 | 保持不变的能力 |
|---|---|---|
| OTP 首页条目 | 长按菜单中的“生成迁移二维码”继续用于单条迁移。 | 复制、编辑、置顶、删除与倒计时。 |
| OTP 首页导出 | 导出格式菜单新增“加密迁移二维码（全部）”。 | TXT、JSON 与 Google Authenticator 导出。 |
| 首页扫码添加 | `otpauth://` 继续按原逻辑直接添加；`OTPT1.` 进入单条迁移；`OTPB1.` 进入全量二维码收集。 | 相机扫码和相册识别。 |
| 数据管理 → 微信导入导出 | 新增“导出全部 OTP 为二维码”；微信 `.bak` 文件入口仍保留。 | 加密文件导出、微信文件导入、WebDAV、回收站。 |
| 设置 → 备份密码 | 首条数据保存后仍只提示一次备份密码设置；全量二维码不复用该全局备份密码。 | 空备份密码二次确认和其他设置。 |

## 三、导出与导入交互

### 3.1 统一保护表单

单条和全量二维码的导出表单使用同一交互规则：只有一个访问密码输入框，旁边提供“👁 显示/隐藏”切换，不再要求重复输入。用户可留空密码并选择有效期，也可设置密码并选择“不设有效期”。

| 用户选择 | 是否可生成 | 导入表现 |
|---|---:|---|
| 6 位以上访问密码 + 任意有效期 | 可以 | 收齐二维码后要求输入同一密码。 |
| 仅 6 位以上访问密码 | 可以 | 可长期使用，仍需密码。 |
| 仅有效期 | 可以，但会二次提示风险 | 在有效期内无需密码；二维码泄露即可能被导入。 |
| 不设置密码且不设有效期 | 不可以 | 页面提示至少选择一项保护。 |
| 1–5 位密码 | 不可以 | 页面提示密码至少 6 位。 |

> 访问密码只保留在当前页面内存中，用于派生加密密钥；不会保存至设置、普通二维码历史或导出记录。

### 3.2 单条 OTP 迁移

发送方从条目长按菜单进入，设置保护后展示一张二维码和倒计时。接收方在首页既有“扫码添加”扫描，输入密码（若导出方设置了密码）后写入本地。相同密钥、发行商和账号的 OTP 不会重复添加。

### 3.3 全量 OTP 迁移

全部 OTP 不会被强行塞进一张过密二维码。发送方的完整加密容器会自动拆成多张可扫描二维码，并显示“第 *n* / *总数* 张”的上、下一张控制。接收方扫描第一张后进入连续收集页；可以使用相机或相册，扫描顺序不影响结果。收齐同一组二维码后才显示密码输入与导入按钮。

| 阶段 | 页面行为 | 安全与一致性处理 |
|---|---|---|
| 生成 | 本地加密全部 OTP 并自动拆分二维码。 | 单片原始二进制最多 520 字节，最多 30 张；超过限制时改用微信加密文件。 |
| 展示 | 发送方手动切换“上一张/下一张”。 | 二维码不进入普通二维码历史。 |
| 收集 | 接收方显示已收集数量与进度。 | 会话 ID、总张数不同的二维码不能混入；重复扫描不重复计数。 |
| 解密 | 收齐后输入密码或留空。 | 先检查过期，再进行 AES-GCM 认证解密。 |
| 合并 | 一次性写入本地 OTP 列表。 | 按密钥、发行商、账号去重；只持久化一次并显示新增与重复数量。 |

## 四、协议与加密

两个协议均为 ASCII 安全文本，适合二维码 Byte 模式。加密、解密、二维码绘制和数据合并均在小程序本地完成。

| 用途 | 二维码前缀 | 二进制 Magic | 明文类型 |
|---|---|---|---|
| 单条 OTP | `OTPT1.` | `OTQ1` | `{ type: "otp-transfer", ...单条 OTP 字段 }` |
| 全部 OTP 分片 | `OTPB1.` | `OTB1` | `{ type: "otp-bundle", tokens: [...OTP] }` |

两个容器均使用 **PBKDF2-HMAC-SHA-256** 从访问密码和随机盐派生密钥，再使用 **AES-GCM** 加密及认证。KDF 的盐和成本因子用于提高离线口令猜测的成本。[1] 头部中的版本、迭代次数、创建时间、到期时间、盐和 IV 会作为 AES-GCM AAD 被认证，篡改到期时间或密码学参数会造成解密失败。

全量二维码的每一张采用如下包装：

```text
OTPB1.<sessionId>.<part>-<total>.<Base64URL(二进制分片)>
```

`sessionId`、当前张序号和总张数只用于扫码收集和防止不同组混用；它们本身不承担机密性或完整性承诺。真正的完整性由所有分片重组后对 AES-GCM 容器的认证保证；插入、替换、删除或重排分片都会导致收集失败或最终认证解密失败。

## 五、有效期与无密码模式的真实含义

| 说法 | 是否正确 | 产品文案 |
|---|---|---|
| “到期后，正常导入流程会拒绝二维码” | 正确 | “二维码将在指定时间后失效。” |
| “仅设置有效期也能保密” | 不正确 | “仅有效期模式不要求密码，请勿公开二维码。” |
| “过期后绝对无法恢复” | 不正确 | 不做此类承诺。 |
| “可远程撤销或保证只能使用一次” | 不支持 | 这需要联网服务端状态。 |
| “修改导入设备时间可能影响预检” | 可能 | “有效期由接收设备本地时间检查，不能替代访问密码。” |

静态二维码编码的是固定内容；与依赖服务端状态的动态二维码不同，离线二维码无法天然实现远程失效。[2] 因而访问密码是保密性的主要手段，有效期只是辅助限制。

## 六、失败处理

| 情况 | 用户提示或行为 |
|---|---|
| 扫描普通 `otpauth://` | 保持原有直接添加流程。 |
| 扫描非本功能二维码 | 提示无法识别，不进入密码页。 |
| 分片未收齐 | 显示已收集数量，继续扫描缺少的二维码。 |
| 扫描了不同会话的分片 | 提示不属于同一组，可继续当前组或重新开始。 |
| 分片过多或载荷过大 | 发送方提示改用微信加密文件导出。 |
| 已过期 | 在密码输入与写入前拒绝导入。 |
| 密码错误、容器损坏或分片被篡改 | 统一提示“访问密码错误，或二维码已损坏”。 |
| OTP 已存在 | 不创建重复条目，并在成功统计中显示重复数量。 |
